提到持续学习，人们通常会想到重新训练模型、更新权重，或者使用新数据进行微调。

但现实中，许多企业使用的是闭源模型。开发者可以调用模型，却无法访问或修改模型权重。那么，这些 AI 系统是否只能保持静态，直到模型供应商发布下一代模型？

在 Agentic AI Summit 2026 上，Replit 总裁 Michele Catasta 在 **Continual Learning for Agents** 演讲中给出了另一种答案：

> 即使不改变模型本身，我们仍然可以持续改进模型周围的系统，让整个 Agent 产品从真实使用中学习。

这种学习发生在 Agent 的 harness，也就是模型外部的运行环境中。

## Agent 的能力不只取决于模型

一个生产环境中的 Agent，通常不只是一个大语言模型。

它还包括：

* 系统提示和任务指令
* 可调用的工具
* 上下文检索机制
* 执行环境
* 重试和错误处理逻辑
* 权限与安全限制
* 多 Agent 编排
* 记忆和历史信息
* 结果评估机制

这些部分共同决定了 Agent 最终能否可靠地完成任务。

因此，即使底层模型保持不变，修改工具、工作流、上下文和执行逻辑，也可能显著改善 Agent 的表现。

严格来说，这并不是模型参数层面的持续学习，而是系统层面的持续改进。但从用户角度看，结果非常相似：Agent 会随着使用逐渐变得更加可靠。

## 为什么固定评测还不够

AI 团队通常使用 benchmark 和 evaluation 检查系统表现。

这种方法非常重要，因为结果通常很清晰：

1. 修改 Agent harness。
2. 运行评测集。
3. 得到一个分数。
4. 判断能力提升还是发生回归。

问题在于，固定评测只能覆盖预先设定好的任务。

一个评测集可能包含几十个或几百个案例，但生产环境中每天可能发生数百万次真实交互。用户会提出评测设计者从未想到的问题，也会用意料之外的方式操作产品。

固定评测可以告诉团队 Agent 在已知场景中的表现，却很难发现真实世界中的长尾问题。

而这些长尾问题往往最有价值，因为它们揭示了系统真正的边界。

## 生产 Trace 是持续学习的数据来源

当一个 AI 产品获得大量真实用户后，每天都会产生海量 traces。

一条 trace 可能包括：

* 用户提出了什么请求
* Agent 获取了哪些上下文
* Agent 调用了哪些工具
* 每一步返回了什么结果
* Agent 如何处理错误
* 最终是否完成任务
* 用户是否满意
* 整个过程消耗了多少时间和成本

这些数据不仅可以用于训练模型，也可以直接用于改进 Agent 系统。

通过分析 traces，团队能够回答：

* Agent 经常在哪些步骤失败？
* 哪些工具定义容易让模型误解？
* 为什么用户对某类回答不满意？
* 哪些异常正在重复发生？
* 哪些问题来自模型？
* 哪些问题来自基础设施？
* 哪些 Prompt 或工作流需要调整？

Michele 提出的核心思想是，不要只是偶尔检查这些数据，而应该将它们接入一个持续运行的反馈闭环。

## 一个自动改进 Agent 的闭环

他介绍的流程可以概括为以下几个步骤。

### 1. 收集生产环境中的 Traces

系统持续记录 Agent 在真实任务中的执行过程。

由于数据量可能达到每天数百万条，人工逐条检查并不现实。

### 2. 对 Traces 进行语义聚类

系统首先使用相对基础的机器学习方法，将行为相似的 traces 聚集在一起。

绝大多数正常行为不需要深入分析。团队真正关心的是突然出现的新集群，以及频率异常上升的小集群。

它们通常代表某种新的失败模式。

### 3. 找到异常和长尾行为

单独查看时，一些失败可能看起来完全不同。

Agent 具有非确定性。面对同一个底层问题，它可能在不同请求中采用不同的推理和排错策略。

语义聚类可以帮助团队发现，这些表面不同的失败其实拥有同一个根本原因。

### 4. 使用前沿模型分析根因

发现异常集群后，系统再使用能力更强的模型阅读相关 traces，判断问题究竟发生在哪里。

问题可能来自：

* Prompt 不清楚
* 工具描述不准确
* 上下文缺失
* API 返回格式变化
* 执行环境尚未准备完成
* 重试逻辑不合理
* Agent 做出了错误的恢复选择

### 5. 自动生成修复 PR

识别根因后，系统可以直接修改 harness、代码或基础设施配置，并生成 Pull Request。

这意味着，生产环境中的失败不再只是等待工程师手动排查，而是可以自动转化为候选修复方案。

### 6. 通过 A/B Test 验证

自动生成 PR 并不意味着修改应该直接上线。

团队仍然需要运行实验，观察它对不同指标的影响，例如：

* 任务成功率
* 响应速度
* 计算成本
* 用户满意度
* 工具调用次数
* 错误恢复能力

实际结果通常不是简单的“全部变好”或“全部变差”。

一个修改可能提高速度，却降低准确率；也可能降低成本，却让用户体验变差。

因此，最终是否上线，仍然需要人类结合产品目标做出判断。

## 一个很难通过传统监控发现的故障

Michele 分享了一个非常具体的案例。

他们的系统每天会为用户启动大量虚拟机。在一个正常流程中，Agent harness 和虚拟机都需要准备完成，Agent 才能开始执行代码和调用工具。

但偶尔会发生一种长尾问题：

> Agent 已经准备好了，虚拟机却还没有完全启动。

此时，Agent 尝试执行代码会失败。

由于 Agent 很倾向于主动排查问题，它不会简单等待，而是会尝试不同的调试方式：

* 检查命令是否正确
* 尝试其他工具
* 怀疑权限问题
* 修改执行步骤
* 重新运行代码

不同请求中的错误表现各不相同，因此人工查看单条日志时，很难发现它们属于同一个问题。

这个故障发生频率也不够高，未必会明显出现在常规监控仪表盘中。

但是，当系统对大量 traces 进行聚类后，这些看似不同的失败被归入同一个异常集群。分析系统发现，它们的共同原因是虚拟机启动时间偶尔慢于 Agent harness。

随后，系统生成了对应的修复 PR。

这个案例说明，生产 traces 不只是调试记录，也可以成为 Agent 持续改进的学习信号。

## Evaluation 不应只是上线前的检查

传统软件开发流程中，evaluation 经常被放在最后：

> 开发完成后运行测试，然后决定是否发布。

Michele 建议换一种理解方式：

> Evaluation 不应该只是一个发布前的布尔判断，而应该成为持续改进 Agent 的引擎。

新的流程更像是：

```text
生产使用
→ 收集 traces
→ 发现异常模式
→ 分析根因
→ 自动生成修改
→ A/B Test
→ 人类决策
→ 部署改进
→ 继续收集新的 traces
```

在这个循环中，每一次真实失败都可能帮助系统变得更好。

## 人类的角色并没有消失

即使异常分析和 PR 生成可以大量自动化，人类依然承担几个关键职责：

* 定义哪些指标最重要
* 判断速度、成本和质量之间的取舍
* 审核高风险修改
* 决定哪些实验应该继续
* 识别局部修复是否掩盖了更深层的架构问题
* 确定产品长期应该朝哪个方向发展

Agent 可以帮助人类更快地发现问题和提出解决方案，但它未必知道企业最终想优化的是什么。

这也是为什么持续学习系统仍然需要 human in the loop。

## 从持续学习走向 Omniscient Agents

Alex Graveley 在 **Omniscient Agents** 演讲中讨论了一个更远的方向。

他认为，Agent 的责任范围正在沿着一个复杂度阶梯不断扩大：

```text
工具调用
→ Commit
→ Pull Request
→ 多个 Pull Requests
→ Feature
→ Project
→ Product
```

Agent 如果只会修改代码，就很难独立负责一个完整功能。

要负责 Feature 或 Product，它还必须能够：

* 读取真实业务数据
* 观察用户反馈
* 运行实验
* 监控生产系统
* 判断功能是否改善留存或收入
* 根据结果扩大部署或回滚

Alex 将这种能力归纳为两个维度。

### Insight

Agent 能看到什么，以及它能否从这些信息中形成正确判断。

它需要从只看到代码，逐渐发展到理解用户、产品、实验和整个业务。

### Control

Agent 能够对真实系统做什么。

它需要从提出建议，逐渐发展到修改代码、部署功能、运行实验和调整线上系统。

从这个角度看，Michele 的持续学习闭环，正是 Omniscient Agent 所需要的一项基础能力。

一个 Agent 如果要自主负责产品，就必须能够观察真实结果、发现异常、修正自身的执行方式，并继续迭代。

## 结语

未来 Agent 的进步不一定只来自更大的模型或更多参数。

大量改进可能来自模型之外：

* 更好的工具
* 更准确的上下文
* 更完整的生产 traces
* 更有效的异常检测
* 更可靠的实验机制
* 更清晰的人类决策边界

即使模型权重保持不变，一个设计良好的反馈系统，也可以让 Agent 随着每一次真实使用持续进化。

真正重要的问题，可能不再只是“我们使用了哪个模型”，而是：

> 我们是否建立了一个能够从真实世界中持续学习的 Agent 系统？
